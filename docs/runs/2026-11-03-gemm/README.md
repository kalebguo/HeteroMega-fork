# 2026-11-03: a faster GPU branch for `merged_ffn` at two inflight chunks (AUP)

**Measured.** With all kept switches, `merged_ffn` P8192 prefills 1024 tokens in 1005.5 ms. The archived `heteromosaic` records are 1309.6-1355.5 ms, so the
speedup is 1.30-1.35x. These rows are not paired: the user asked to compare the latest code with the archived records and not to run `heteromosaic` again.

| P6400 | 1032.3 | 1.269x, 1.289x | 448 | 0 |
| P7168 | 1046.7 | 1.251x, 1.272x | 448 | 0 |

All rows are in `latest-vs-heteromosaic-records.csv`, generated by `tools/split_model/heteromosaic_records.py`. The run with these switches is job `gemm-final`,
10:44-11:13 UTC Nov 3 (04:44-05:13 CST). The box's checkout is an overlay on `5bd4648e`; `final/source-sha256.txt` holds the hash of each source file,
and each matches the commit that adds this directory.

The switches, all off by default so that the baselines stay reproducible:

```bash
HETEROMEGA_GEMM=fast HETEROMEGA_GEMM_UNCACHED=1 HETEROMEGA_SDPA=fast HETEROMEGA_SDPA_TO_O=1 HETEROMEGA_FFN_FUSE=1 HETEROMEGA_FFN_SLOT_BO=2 HETEROMEGA_RESIDUAL_NORM=1
```

Stages of attention other than the GEMMs, wall time per chunk-layer while the GPU is shared, P8192, chunk 0 / chunk 1: rope 0.50 / 0.25, kv 0.21 / 0.15, `sdpa_bf16` 0.60 / 0.90,
`ready` 0.70 / 0.50 ms. Together 2.0 / 1.8 ms of a 31 ms cycle. Full table: `stages/stage-report-4.txt`.

**Analysis.**

- **GPU time in attention.** The non-GEMM stages are about 6% of the cycle in wall time, and they overlap with the other chunk. Removing half of them would give under 3% (estimated).
- **NPU queue.** The mutex wait exists because the two chunks reach the NPU close together. It is not the bound: the GPU is busy 96.6-100%, so a shorter queue only moves the wait to the GPU side.
  With `GPU_MAX_HW_QUEUES=8`, the 6-10 ms `h2d` on one slot goes to 0.3-0.5 ms, `gpu_wait` grows by the same amount and the total does not change.
- **Copies.** `SLOT_BO=2` removed the CPU copies. The two HIP copies left cost 0.3-0.4 ms on the NPU path, and removing them made the result slower.
- **Stop point.** P8192 is close to balance: GPU idle 3.4%, NPU idle 12.9%. A further gain must come from the GEMMs, which take about 13.7 of the GPU's about 15.7 ms per chunk-layer (estimated from `gemm-stages2` and
  `gemm-fuse`). The list below shows what did not work there.

## Tried without a gain (measured unless labeled)

Blocks of R = 2 and R = 4 output tiles (`gemm-rblock*`); workgroup order chunks; NPU buffers on 2 MB pages alone (`gemm-thp`); a helper wave that prefetches; weights in USWC, host or fine-grained memory
(`gemm-pools`, `gemm-unc`); VRAM, which HIP and HSA cannot reach on this APU (`gemm-vram`); a separate or low priority stream for the GPU branch; a single HW queue; `GPU_MAX_HW_QUEUES=8` (`gemm-stages3`); own NPU
buffers with copies through XRT (`SLOT_BO=1`, within noise); zero copy (`gemm-ab9`).

The NPU slows the GPU through memory, not through the clock (`gemm-interfere2`, `gemm-abl*`): GPU ALU and WMMA loops keep their speed, DRAM reads fall from 15.7-18 to 13.4-14 GB/s, and a GEMM goes from 4.63 to 6.90 ms.
Uncached weights bring the 6.90 ms part way back.

## Limits

- 1024 tokens, two inflight chunks, one prompt for timing, on the HX 370 only. No paired `heteromosaic` run: its records spread over 1309.6-1355.5 ms.
- Not measured: energy per prefill (paused by the user), other prompt lengths, one inflight chunk with these switches.
- The first sample of a process is the slowest, up to 1699 ms. It stays in the pooled median.
- Peak GTT is 10951 MB of 11818 MB. Uncached copies replace the FFN slices, but the attention weights are held twice (about 0.7 GB). A failed copy prints `UNCACHED_FALLBACK` and uses the original weights.
- `test_gpu_ffn` is not valid with `HETEROMEGA_GEMM_UNCACHED=1`, because the test frees weights and reuses their addresses for other weights of the same size. The model's weights stay fixed.

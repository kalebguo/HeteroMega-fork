# Split-ratio cost model: merged GPU+NPU FFN, M=512, H=4096, I=14336

Refit on 2026-11-02 from in-model phase timers and the four measured split points of the Oct 28 sweep. Inputs are measured; everything in the prediction table is estimated. Generated by `python3 tools/split_model/split_cost_model.py --report tools/split_model/REPORT.md`.

The decision below was derived at one inflight chunk. The measured two-inflight results in `docs/runs/2026-11-02-inflight2-*/` are not folded into this report yet.

## Decision

**Do not build other split ratios for prefill latency.** P6400 is within 28 ms of the best valid split in every scenario (2.1% of a 1340 ms prefill; estimated). The measured sweep shows no winner either: P6144 at 14.18 ms and P6656 at 14.35 ms sit inside the spread of the three P6400 blocks (13.87-14.59 ms).

What decides the result is the NPU context change, not the split: see the prefill table below.

## Consistency checks (measured against the model)

- Phases at P6400: 64 x (8.339 + 12.601) = 1340.2 ms; paired evaluation 1340.8 ms.
- Slope check: P4352 predicts a GPU-bound FFN of about 15.0 ms; the sweep's concurrent P4352 is 15.57 ms with a 16.06 ms GPU branch, so it is GPU-bound too.

## What the data cannot determine

1. The in-model GPU branch has no end timer, only the upper bound above. A completion timestamp would fix its level.
2. The sweep's NPU waits are noisy: three P6400 blocks range over 0.52 ms, which is more than the 0.34 ms between P6144 and P6656.
3. With overlapping attention (two inflight chunks) the balance could move toward more NPU channels. Two inflight chunks gain nothing today (`docs/runs/2026-11-02-fix-step2b/README.md`), so this model does not cover it.
4. This model is latency only. Numerics are in `docs/runs/2026-11-02-fix-step5-numerics/` and `docs/runs/2026-11-02-fix-step5b-sampled/`.
